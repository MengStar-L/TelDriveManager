PikPak 转存目标载荷修正设计

项目：TelDriveManager · 日期：2026-08-01 · 状态：已确认

核心决策：仅将分享恢复请求的目标目录字段从无效的扁平 to_parent_id 修正为 PikPak 接受的嵌套结构 to.parent_id。现有隔离目录、全量校验、失败不推送和仅清理自有目录的规则全部保留。

1. 生产证据与根因

2026-08-01 02:46:20（服务器 EDT），PikPak 返回 RESTORE_START，本次隔离目录为 VOyw3hi05ETZwllgHnyyT8Apo2，选择数量为 1。随后 60 秒内该目录始终为 0 个文件， 页面于 02:47:21 报告“应有 1 个文件，实际就绪 0 个”。

当前请求把目标目录写成：

{
  "share_id": "...",
  "pass_code_token": "...",
  "file_ids": ["selected-file-id"],
  "to_parent_id": "owned-scope-id"
}

PikPak 接受请求但静默忽略未知字段。已核对可工作的客户端实现，接口要求：

{
  "share_id": "...",
  "pass_code_token": "...",
  "file_ids": ["selected-file-id"],
  "to": {
    "parent_id": "owned-scope-id"
  }
}

2. 修改范围

文件修改保持不变
app/modules/pikpak/client.py 在 start_isolated_share_restore() 中生成嵌套 to.parent_id。 唯一目录创建、认证请求、错误处理、响应 file_id 忽略策略。
tests/test_pikpak_share_restore_isolation.py 把载荷断言改成嵌套结构，并明确断言不存在扁平字段。 数量、名称、aria2 推送数量、串并行模式和清理所有权测试。

app/modules/pikpak/routes.py、前端、aria2、Telegram、TelDrive 数据库和任务状态均不修改。

3. 数据流与安全边界

  1. 创建唯一的 .teldrive-share-<uuid> 空目录并取得其 ID。
  2. 通过 to.parent_id 把本次勾选文件转存到该目录。
  3. 只轮询该目录；不读取、不遍历 PikPak 响应中的 file_id。
  4. 文件数量和名称与用户选择完全一致后，才允许向 aria2 推送。
  5. 任何超时、额外文件或名称不一致都使整批失败，aria2 调用次数必须为 0。
  6. 结束时只删除步骤 1 创建的目录 ID。
既有误落文件：错误载荷可能已把刚才勾选的文件转存到 PikPak 默认目录。 因为该请求没有记录一个可证明归属的返回文件 ID，程序不得猜测并自动删除它；自动清理只处理本次明确创建的隔离目录。

4. 错误处理

  • 接口拒绝恢复请求：删除本次隔离目录并返回失败。
  • 接口返回 RESTORE_START 但目录未就绪：保持当前超时和失败关闭行为，不推送链接。
  • 隔离目录出现多于所选数量的文件：立即失败，不筛选、不继续。
  • 清理失败：记录明确的隔离目录 ID，但不扩大删除范围。

5. 验证与上线

自动验证

  • 载荷精确等于 {"to": {"parent_id": "owned-scope"}}，且没有 to_parent_id。
  • 14 个 PikPak 分享隔离专项测试全部通过。
  • 完整 Python 测试套件全部通过，远端 py_compile 通过。

生产验证

  1. 备份当前失败关闭版本的 client.py，仅部署修正后的该文件。
  2. 重启服务并确认 active、HTTP 可达、启动日志无致命错误。
  3. 用户重新解析同一分享，只勾选一个文件并推送。
  4. 确认隔离目录就绪数为 1、新增 aria2 GID 数为 1、文件名恰好为所选文件。

任何数量不一致都停止验证并恢复部署前备份，不引入名称过滤或默认目录扫描作为补救。

6. 验收条件

  • 同一复现操作不再出现“应有 1 个，实际 0 个”的目标目录超时。
  • 只勾选一个分享文件时，aria2 只新增一个对应任务。
  • 旧的复用目录 ID 仍不会成为解析根目录或清理目标。
  • 本次修改不改变 Telegram 删除、TelDrive 上传或其他 PikPak 工作流。
本规格只处理已确认的 PikPak 分享恢复目标字段错误，不包含其他重构或自动清理历史误落文件。
