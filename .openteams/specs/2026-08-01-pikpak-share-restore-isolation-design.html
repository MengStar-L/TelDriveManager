PikPak 分享转存隔离设计

项目：TelDriveManager · 日期：2026-08-01 · 状态：待书面审阅

核心决策：PikPak 分享下载的二次直链解析必须以“本次操作新建的空隔离目录”为唯一数据源。 程序不再递归解析 restore.file_id，也不从错误结果中按名称或大小挑选文件。无法建立或确认隔离边界时， 整批停止且不向 aria2 推送任何链接。

1. 已确认的故障

服务器证据：分享结果页解析到 paid_4k.mp4 与 paid_8k.mp4；用户提交数量为 1。 转存接口随后返回一个 file_id，现有程序将其当作精确目标递归解析，得到两个旧的 SAVR-1127 文件和一个 paid_8k.mp4，并向 aria2 推送了 3 条链接。

aria2 只接收了上游交给它的三条直链，没有自行生成额外文件。本次故障点位于分享下载阶段的二次解析链路：

save_share_files(...)
  -> 接受 restore.file_id
  -> wait_for_download_urls(file_id)
  -> 若 file_id 是目录则递归列出全部子项
  -> 未确认目录是否只属于本次操作便推送 aria2

初次分享列表解析器能正确展示分享中的文件，不是本次错误来源。需要修复的是转存后的直链解析边界。

2. 目标与非目标

目标

  • 用户勾选一个分享文件时，二次解析只能看到该次操作转存的内容。
  • 不再把 PikPak 返回的外层 file_id 视为可信解析根。
  • 即使 PikPak 返回复用目录、忽略目标目录或响应字段不完整，也不会推送无关链接。
  • 清理动作只允许删除本次由 TelDriveManager 创建并记录的隔离目录。
  • 保持现有分享解析界面、勾选方式、目录结构选项、重命名和 aria2/TelDrive 后续流程。

非目标

  • 不通过文件名或大小过滤复用目录中的内容来掩盖解析边界错误。
  • 不修改磁链解析、RSS 解析或 aria2 会话恢复行为。
  • 不清理历史遗留的 PikPak 文件或目录。
  • 不依赖人工预先清空 PikPak 根目录或保存目录。

3. 方案比较

方案优点限制结论
每批任务使用独立空目录 解析范围由程序创建并控制；不依赖不稳定的返回 ID 语义；可安全清理 需要调用带 to_parent_id 的 restore 请求，并等待隔离目录内容就绪 采用
只接受 task_info[].file_id 代码改动较小；不递归外层目录 本次真实响应没有 task_info，正常大文件会频繁失败 不采用
轮询 restore_task_id 理论上可以等待异步转存结束后获取真实文件 ID PikPak 任务完成响应可能仍不提供真实文件 ID，仓库历史尝试已暴露该不确定性 不作为主路径

4. 新的数据流

  1. 前端继续提交已勾选的分享文件 ID、原始路径及现有下载选项。
  2. 后台校验文件 ID 非空后，为该批任务生成不可预测的唯一目录名。
  3. 通过当前 PikPak 客户端的认证请求能力创建空目录，并取得明确的目录 ID。
  4. 后台调用 PikPak restore 接口，将原有的 share_id、pass_code_token、file_ids 与新目录 ID 一并提交为 to_parent_id。
  5. 后台忽略响应中的 file_id 作为解析根，只把响应状态用于判断请求是否被接受。
  6. 直链解析器从隔离目录的直接子项开始轮询和递归，直到所选文件全部就绪或超时；临时目录名不进入结果路径。
  7. 只有隔离目录内的解析结果才进入现有排序、路径处理和 aria2 推送流程。
  8. 任务完成、失败或取消后，后台只清理第 3 步创建并登记的目录 ID。
已勾选 file_ids
  -> 创建唯一空目录 owned_scope_id
  -> restore(..., to_parent_id=owned_scope_id)
  -> 仅轮询 owned_scope_id
  -> 生成本批直链
  -> 推送 aria2
  -> 删除 owned_scope_id

5. 组件边界

PikPak 客户端封装

app/modules/pikpak/client.py 负责创建隔离目录、发送带 to_parent_id 的 restore 请求以及返回隔离范围 ID。实现复用 PikPak 客户端自身的认证请求方法，不单独读取访问令牌，也不创建另一套 HTTP 会话。

创建目录或 restore 请求失败时直接抛出错误。禁止回退到不带 to_parent_id 的普通 restore，也禁止回退到响应中的外层 file_id。

分享下载编排

app/modules/pikpak/routes.py 负责持有本次隔离目录 ID、等待直链、调用现有推送流程并在 finally 中清理。隔离目录 ID 与“待解析文件 ID”分开表达，避免再次把目录所有权和内容目标混为一谈。

解析结果的相对路径以初次分享解析提交的 file_paths 为准。隔离目录只提供所有权和枚举边界，不参与 aria2 下载目录或 TelDrive 目标路径的构造。

前端

现有分享结果展示、复选框和“推送下载链接”按钮不变。错误提示需要明确说明“PikPak 未将所选文件转存到独立目录，本次未向 aria2 推送任何内容”，避免用户误以为任务已部分提交。

6. 就绪与异常判定

  • 隔离目录创建失败：立即停止，不调用 restore。
  • restore 请求失败或明确返回错误：立即停止，不解析、不推送。
  • 隔离目录在超时时间内为空：整批失败，不使用 restore.file_id 补救。
  • 隔离目录出现多于所选文件数量的文件：视为隔离契约被破坏，整批失败，不过滤后继续。
  • 只出现部分所选文件：继续等待至超时；超时后整批失败，不进行部分推送。
  • 所有所选文件就绪：一次性进入推送阶段，保持现有顺序和路径处理。
文件数量、名称和大小可用于检测“隔离契约是否异常”，但不能用于从非隔离目录中筛选结果。解析根必须始终是程序本次创建的目录 ID。

7. 清理安全

当前流程在 finally 中删除 saved_ids，而这些 ID 可能来自 PikPak 响应并指向复用目录。新流程禁止这种做法。

  • 清理函数只接受本次成功创建的 owned_scope_id。
  • 未成功创建隔离目录时，清理集合为空。
  • 不得把 restore.file_id、task_info.file_id 或解析出的子文件 ID 加入目录清理集合。
  • 清理失败只记录错误，不扩大删除范围，也不尝试扫描并删除同名目录。
  • 进程异常退出可能留下程序创建的临时目录；相比猜测所有权并自动删除，保留孤立目录是可接受的安全退化。

8. 兼容性

  • 后端接口路径和现有请求字段保持兼容。
  • 旧版 PikPak Python 库未公开 to_parent_id 参数，因此通过其已有的认证请求方法调用相同 restore API；不修改第三方包。
  • 磁链、RSS 和 PikPak 账号健康检查继续使用各自现有逻辑。
  • 串行与并行下载模式都消费同一批已隔离解析的文件列表，后续调度行为不变。

9. 验证计划

测试应在调用 aria2 的边界断言 URL 数量，并使用伪造的 PikPak 响应复现本次“一个所选文件、三个递归结果”的故障，证明回归测试在旧实现上失败、在新实现上通过。

10. 完成标准

  • 代码中分享下载链路不再调用 get_download_urls(restore.file_id)。
  • 无法确认隔离目录所有权时，aria2 推送次数为零。
  • 所有清理调用的目标均可追溯到本次 create_folder 返回的 ID。
  • 本次故障的回归测试、现有 PikPak 测试和相关下载调度测试全部通过。
  • 服务器验证时，选择一个文件只产生一个对应的 aria2 GID，不再出现历史目录中的文件。
本规格只描述已确认的 PikPak 分享转存隔离修复。实施前需由用户完成书面审阅确认。
