Telegram 频道与分块清理安全设计

项目：TelDriveManager · 日期：2026-07-31 · 状态：待书面审阅

核心决策：TelDrive 存储频道与 Telegram 监听频道是同一个资源边界，系统只保留一个权威配置 [teldrive].channel_id。前三条已确认需要的删除行为保持不变；上传分块清理改为“证据不足时绝不删除”； 四类 Telegram 删除操作全部写入带完整时间和结果状态的独立审计日志。

1. 背景与问题

当前系统要求分别填写 [teldrive].channel_id 和 [telegram].channel_id，但产品语义要求它们指向同一频道。双配置没有提供能力，只引入了漂移和误操作风险。

此外，上传去重和污染会话恢复会从 TelDrive 返回的 part 数据提取消息 ID，却固定向 Telegram 监听频道执行删除。即使当前两个频道相同，这条路径仍缺少对“该消息是否正在被有效文件引用”和“候选 ID 是否来自当前上传会话”的强校验。

2. 目标与非目标

目标

  • 网页、初始化向导和配置文件只暴露一个频道 ID。
  • 保留同名消息删除、回源成功后删除源消息、TelDrive 文件删除后同步清理 Telegram 消息三项现有功能。
  • 第四条分块清理只有在当前上传会话、最终文件保护集合和活跃文件引用三方面均可确认时才执行。
  • 任何查询失败、配置冲突或数据不一致均保守退化为“记录待清理项，不删除 Telegram 消息”。
  • 四类 Telegram 删除操作均具有结构化审计信息，可定位时间、结果、原因、文件、任务、上传会话、频道和消息 ID。
  • 在 Telegram 监听中转页面提供独立的 Telegram 删除日志视图，并能实时看到新记录。

非目标

  • 不取消前三项业务删除能力。
  • 不自动清理历史遗留的 upload_orphans 记录。
  • 不修改 TelDrive 服务端协议或 Telegram 权限模型。
  • 不承诺外部系统、人工管理员或 Telegram 自身绝不会删除消息。

3. 单一频道配置

权威字段

[teldrive].channel_id 是唯一保存和运行时读取的频道 ID。Telegram 新消息监听、删除同步、回源源消息处理及上传分块清理均使用这一权威值。

旧配置迁移

旧配置状态加载行为下次保存
只有 teldrive.channel_id直接使用只保存权威字段
只有 telegram.channel_id迁移为权威字段并记录一次迁移日志删除旧字段，只保存权威字段
两个值等价，包括 -100 前缀差异规范化后使用 TelDrive 值删除旧字段
两个有效值不等价进入配置冲突状态，不启动 Telegram 删除能力，也不执行第四条清理用户在单一输入框确认后保存

界面

  • TelDrive 配置区保留一个“Telegram 存储/监听频道 ID”输入。
  • Telegram 配置区和初始化向导的 Telegram 步骤移除重复频道输入。
  • 连接测试、配置健康检查和设置保存均读取同一个输入值。
  • config.example.toml 和 README 不再展示 [telegram].channel_id。
  • Telegram 监听中转页面顶部使用三个互斥视图选项：运行日志、TelDrive 删除日志、Telegram 删除日志。
  • Telegram 删除日志按最新删除时间优先展示；清空按钮只清除当前日志流，不触发任何文件或消息删除。

4. 第四条清理的安全边界

第四条包含两种不同操作：

  1. 成功上传后的重复块回收：文件记录已成功创建，只删除未被最终文件选中的重复或越界块。
  2. 污染上传会话重置：文件记录未成功创建，当前上传会话需废弃后重传。

统一删除前置条件

  1. 权威频道 ID 有效，且不存在旧配置冲突。
  2. 候选 ID 是正整数、去重后非空，并明确关联当前 task_id 与 upload_id。
  3. 成功取得当前上传会话的实时 part 列表；不得仅凭内存缓存或数据库中的旧 checkpoint 删除。
  4. 成功取得权威频道中所有活跃 TelDrive 文件引用的 part ID；查询失败返回“未知”，不得当作空集合。
  5. 候选 ID 不在活跃文件引用集合中。
  6. 成功上传后的清理还必须保证候选 ID 不在本次最终文件的 remote_parts 保护集合中。
候选 part IDs - 当前文件 remote_parts IDs - 全部 active 文件引用 IDs = 可删除 IDs 任一证据查询失败或集合关系异常 -> 记录 upload_orphans -> 不调用 Telegram delete_messages

重复块回收

文件创建成功后，upload_meta.remote_parts 是最终文件使用的保护集合，upload_meta.orphan_parts 是候选集合。即使服务端把同一个消息 ID 重复返回，集合相减也会保护最终文件正在使用的消息。

污染会话重置

必须用当前 upload_id 实时查询分块。若查询失败、上传 ID 缺失、活跃引用查询失败或 part 数据与当前任务不一致，则跳过 Telegram 删除，写入 upload_orphans 审计记录，清理服务端上传会话状态并继续既有重试流程。保守失败最多留下无用分块，不会阻塞正常上传。

5. 前三项功能保持

功能保持的行为新增约束
同名消息删除新媒体与已映射文件同名时仍立即删除新消息频道来源改为单一权威值
Telegram 回源重传 TelDrive 成功后仍删除源消息源频道必须等于权威频道
删除同步TelDrive 文件确认消失后仍清理对应 Telegram 消息映射、确认轮次和现有保护逻辑不变

6. Telegram 删除审计与错误处理

所有 Telegram delete_messages 调用和被安全规则阻止的删除决策统一写入独立的 telegram_deletions 进度日志流。每次操作只产生一条最终审计记录，结果分为 deleted、failed 和 blocked。

审计覆盖以下四类来源：

  1. 新媒体与已映射文件同名时删除重复消息。
  2. Telegram 回源重传成功后删除源消息。
  3. TelDrive 文件确认消失后同步清理对应 Telegram 消息。
  4. 成功上传后的重复块回收及污染上传会话分块清理。

每条记录至少包含：

  • occurred_at：操作结束时间，持久化为带时区的 ISO 时间；页面显示完整的本地日期和时间 YYYY-MM-DD HH:mm:ss。
  • status：deleted、failed 或 blocked。
  • reason：稳定的机器可读原因码，并在页面映射为中文说明。
  • channel_id、候选消息 ID、实际删除 ID、文件名列表和文件 ID列表。
  • 可用时记录 task_id、job_id、upload_id、最终文件保护 ID和活跃文件保护 ID。
  • 失败错误或阻止原因，例如配置冲突、实时查询失败、活跃引用查询失败或候选全部受保护。

后端提供独立的查询和清空接口；前端在 Telegram 删除日志视图打开时通过现有实时事件连接接收新审计记录， 无需刷新整页。日志沿用现有容量策略进行裁剪，含义是覆盖所有删除来源和结果，而不是无限期增长。

保守原则：删除失败或验证失败不应让上传任务永久失败。系统保留现有“记录孤儿块后继续重试”的恢复能力。

8. 验收标准

  1. 新保存的配置文件只含一个频道 ID，页面和向导也只要求填写一次。
  2. 旧配置中两个等价 ID 可无损加载并在保存后完成迁移。
  3. 旧配置冲突时不会执行任何 Telegram 自动删除，并能在页面或日志中明确定位冲突。
  4. 同一消息 ID同时出现在 remote_parts 与 orphan_parts 时不会被删除。
  5. 任何活跃 TelDrive 文件引用的消息 ID不会被第四条删除。
  6. 实时上传会话查询或活跃引用查询失败时，第四条零次调用 delete_messages，任务仍可重置并重试。
  7. 证据完整的真实孤儿块仍会被自动清理。
  8. 前三项删除行为的现有测试和新增回归测试全部通过。
  9. 四类 Telegram 删除来源在成功、失败或被阻止后均生成一条且仅一条审计记录。
  10. 每条记录包含可显示到秒的完整删除时间、状态、原因、频道和消息 ID。
  11. 页面可在运行日志、TelDrive 删除日志和 Telegram 删除日志之间稳定切换，动态内容不会改变面板尺寸。
  12. Telegram 删除日志视图打开时能实时出现新记录，清空日志不会调用任何 Telegram 或 TelDrive 删除 API。

9. 测试策略

  • 配置单元测试：单字段、旧字段迁移、-100 等价形式、冲突阻断、保存结果。
  • 分块清理单元测试：候选规范化、最终文件保护、活跃文件保护、重复 ID、空集合。
  • 故障测试：上传会话查询异常、数据库查询异常、Telegram 客户端断开、删除 API异常。
  • 业务回归测试：同名消息、回源成功、删除同步三条路径仍调用预期频道和消息 ID。
  • 审计测试：四类来源、三种结果、完整时间、单操作单记录、容量裁剪和敏感信息排除。
  • 接口测试：Telegram 删除日志查询按时间返回、限制条数、独立清空且不影响其他日志流。
  • 前端测试：三态切换、时间格式化、状态样式、空状态、实时追加和清空确认。
  • 完整测试套件和配置读写烟雾测试。
本设计以数据保护优先：无法证明一个分块是孤儿时，宁可保留无用消息，也不删除可能仍被文件使用的消息。
