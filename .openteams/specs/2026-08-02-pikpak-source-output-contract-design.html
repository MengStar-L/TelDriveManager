PikPak 解析身份与输出命名契约设计

日期：2026-08-02 · 状态：用户已确认修订方向，待书面规格复核

适用范围：PikPak 分享链接解析、Jellyfin 格式化、隔离恢复、路径绑定与 aria2/串行队列推送。

结论

当前链路把“源文件身份”和“最终输出名称”混在同一组 name/path 字段中。Jellyfin 格式化直接改写这些字段后，后端使用新名称校验 PikPak 返回的原文件，导致正确文件被误判为恢复结果不一致。

核心规则：文件身份只由分享作用域和 source_file_id 决定；名称只作为元数据。Jellyfin、层级重命名和 aria2 输出名均不得改变或参与源文件身份判断。
真实接口确认：深层分享 URL 最后一段是 PikPak 的不透明目标定位符，不是文件 ID。它必须作为首个分享请求的 parent_id 原样发送，但不得与返回节点的 id 或 parent_id 比较。

已确认故障链路

  1. 分享解析返回原始 id/name/path。
  2. 前端 Jellyfin 格式化就地改写 item.name 和 item.path。
  3. 下载请求把已经格式化的路径作为 file_paths 发送，同时另发 name_overrides。
  4. PikPak 隔离恢复返回原始文件名。
  5. 后端在应用 name_overrides 前，按名称比较隔离结果与 file_paths，因此产生“隔离解析结果与勾选文件不一致”。
  6. 安全校验在 aria2 前中止，所以本次没有推送错误下载链接。

目标与非目标

目标

  • 深层分享链接的目标定位符必须显式发送，不允许静默省略定位符后重试分享根目录。
  • 解析产生的源 ID、源名称和源路径在一次工作流内保持不可变。
  • Jellyfin 格式化只改变预览和最终输出名称。
  • 隔离恢复完全依赖源 ID到目标 ID的任务映射，不按名称或返回顺序猜测。
  • 同名文件、多层目录和格式化后的文件均能稳定绑定到原始路径。

非目标

  • 不放宽现有隔离目录所有权和“整批验证通过后才推送”的安全规则。
  • 不扫描或复用 Pack From Shared，不从其他目录补齐结果。
  • 不改动 Jellyfin 的标题识别算法本身。
  • 不通过删除名称校验后信任返回顺序来绕过问题。

统一数据模型

字段含义可变性用途
target_locator深层分享 URL 中的不透明目标定位符不可变仅作为首个分享请求的 parent_id；不参与文件身份判断
source_file_id分享中的原始文件 ID不可变勾选、恢复、映射与安全校验
source_namePikPak 返回的原始文件名不可变原始元数据与诊断日志
source_path分享作用域内的原始相对路径不可变目录结构映射和层级重命名来源
output_name用户希望写入 aria2/TelDrive 的文件名可变Jellyfin 或层级重命名结果
destination_file_id隔离恢复后产生的网盘文件 ID恢复阶段生成获取直链和清理范围验证

现有接口可暂时保留 id/name/path 作为兼容展示字段，但内部必须将其视为 source_file_id/source_name/source_path，格式化操作不得再改写它们。

端到端数据流

分享 URL
  -> 后端解析 share_id + 可选 target_locator
  -> PikPak 分享接口显式发送 parent_id=target_locator
  -> 不使用省略 target_locator 的根目录请求重试
  -> 只从接口实际返回节点提取真实 source_file_id
  -> 生成不可变 source_file_id/source_name/source_path
  -> 前端树使用 output_name ?? source_name 展示
  -> Jellyfin 只写 output_name
  -> 下载请求发送：
       file_ids[source_file_id]
       file_paths[source_file_id] = source_path
       name_overrides[source_file_id] = output_name
  -> 创建本次唯一隔离目录
  -> 提交恢复并读取 trace_file_ids
  -> 建立 source_file_id -> destination_file_id 映射
  -> 校验映射集合和隔离目录直属成员集合
  -> 每条直链携带 source_file_id + destination_file_id
  -> 按 source_file_id 绑定 source_path 和 output_name
  -> 全部验证通过后推送 aria2/串行队列

组件职责

组件修改后的职责
app/modules/pikpak/client.py 解析分享 ID 和不透明目标定位符并显式请求对应作用域；只从响应节点生成不可变源元数据；提交隔离恢复；解析源 ID到目标 ID映射；直链结果必须携带两个 ID。
app/modules/pikpak/routes.py 按 source_file_id 校验请求、绑定原始路径和输出名；不得再比较文件名集合；全部验证完成后才允许推送。
app/static/app.js 保持源字段不可变；格式化只设置 output_name；请求中的路径和名称覆盖都按源 ID 构造。
自动化测试 覆盖深层链接作用域、不可变字段、同名文件、Jellyfin 格式化、恢复映射和失败零推送。

请求契约

{
  "share_id": "分享 ID",
  "file_ids": ["source-file-1", "source-file-2"],
  "file_paths": {
    "source-file-1": "原始目录/原始文件名.mkv",
    "source-file-2": "另一目录/同名文件.mkv"
  },
  "name_overrides": {
    "source-file-1": "中文标题 S01E01.mkv",
    "source-file-2": "中文标题 S01E02.mkv"
  }
}
  • file_paths 始终是原始路径，Jellyfin 格式化前后必须完全相同。
  • name_overrides 改为按源 ID 建键，避免同名文件覆盖。
  • 没有格式化的文件可以省略覆盖项，最终沿用原始文件名或层级重命名结果。

命名与路径优先级

  1. 目录结构始终从 source_path 计算，不读取 output_name。
  2. 启用层级重命名时，从 source_path 的父目录生成候选输出名。
  3. 存在 Jellyfin name_overrides[source_file_id] 时，它覆盖层级重命名候选名。
  4. 两项均未启用时，最终输出名为 source_name。
名称优先级只决定输出，不得改变源 ID、恢复目标 ID、直链归属或目录成员校验。

作用域与失败策略

  • 后端自行解析分享 URL，得到 share_id 与可选 target_locator；客户端方法不再依赖 SDK 内部正则隐式决定作用域。
  • 深层链接有 target_locator 时，首个 /drive/v1/share 请求必须显式发送 parent_id=target_locator；该值是 API 定位符，不是文件 ID。
  • 客户端不得把 target_locator 与响应节点的 id/parent_id 比较，也不得调用 /share/detail 把它当作目录 ID。真实源 ID 只能来自首个响应及其后按真实目录 ID 递归得到的节点。
  • 首个请求失败、响应格式无效或没有可解析节点时直接失败；禁止移除 target_locator 后再次请求分享根目录作为回退。
  • 恢复任务源 ID 集合必须等于勾选 ID 集合；目标 ID 集合必须等于隔离目录直属成员集合。
  • 每条直链必须携带可回溯的 source_file_id。缺失、重复或未知 ID 时整批失败。
  • 任何失败路径向 aria2 和串行队列推送 0 条链接，并且只清理本次创建的隔离目录。
禁止省略目标定位符重试分享根目录，禁止将目标定位符冒充文件 ID，禁止按名称搜索替代文件，禁止按返回顺序猜测源文件，禁止部分成功后继续推送。

测试与验收

前端测试

  • Jellyfin 格式化前后 source_file_id/source_name/source_path 不变。
  • 树中显示格式化名称，但请求 file_paths 仍为原始路径。
  • name_overrides 按源 ID 建键；两个同名文件不会互相覆盖。

后端测试

  • 正确恢复映射配合任意输出名均能通过，不再发生名称误判。
  • 源 ID 缺失、多余、重复，或隔离目录成员不一致时推送 0 条。
  • 同名文件按照源 ID 绑定各自原始路径和输出名。
  • 深层分享请求必须携带 URL 中的目标定位符；接口失败时不得发起省略定位符的根目录重试。
  • 目标定位符与响应节点 ID 不同仍可正常解析，响应节点真实 ID 成为 source_file_id。
  • Jellyfin、层级重命名、维持目录结构四种组合均覆盖。

真实链路验收

  1. 使用出现错误的深层分享链接，确认请求携带目标定位符，并记录解析出的真实源 ID 和源路径，不触发 aria2。
  2. 对同一批 12 个文件先执行 Jellyfin 格式化，再提交隔离恢复。
  3. 确认任务映射、隔离目录成员和选中 ID 完全一致。
  4. 确认 aria2 恰好收到 12 条链接，输出名为 Jellyfin 名称，目录仍来自原始路径。
  5. 确认隔离目录清理后不触碰其他 PikPak 文件或目录。

完成标准

  • 深层链接目标定位符被显式发送，且不会因被误当作文件 ID 而拒绝正确响应。
  • Jellyfin 格式化后可以正常完成隔离恢复和推送。
  • 所有文件身份判断均以源 ID/恢复目标 ID 为依据；目标定位符只决定首个请求作用域，代码中不存在名称集合或定位符身份校验。
  • 自动化测试通过，真实 12 文件场景通过，aria2 推送数量与勾选数量严格一致。
